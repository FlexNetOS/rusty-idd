# upgrade-codex-harness-rusty-idd-flow - Design

## Context

Rusty IDD now has graph-backed knowledge artifacts, system architecture
artifacts, operating-model artifacts, integration plans, and an OpenSpec
lifecycle engine. The Codex harness was built earlier around merge execution
and still treats `AI_MERGE/` as a central source of truth in prompts,
invariants, and docs.

Legacy ADR-0003 made `AI_MERGE/` authoritative for integration operations.
That was valid for the earlier merge-control stage, but it conflicts with the
current Rusty IDD model: intent enters through Rusty IDD, graph/context
artifacts shape architecture, OpenSpec records proposal/spec/design/ADR/tasks,
and AI_MERGE is one evidence surface available to that workflow.

The old Claude/Gemini `idd-merge-idd` bridge material carries useful workflow
contracts, but leaving it active teaches agents to bypass the current Rusty IDD
package and OpenSpec lifecycle.

## Goals / Non-Goals

**Goals:**

- Make `.codex` agents and loops follow the real Rusty IDD order:
  intent intake, graph/context, OpenSpec artifacts, implementation, validation,
  evidence.
- Keep AI_MERGE available as an audit and evidence tool.
- Remove AI_MERGE from the harness as the main intent or authoritative control
  plane.
- Require write-capable harness work to have OpenSpec artifact readiness.
- Move reusable merge-goal contracts into a Rusty IDD-owned package.
- Leave `adr/` with only the current Codex harness ADR.

**Non-Goals:**

- Removing `AI_MERGE/` from the repository.
- Rewriting the Rusty IDD lifecycle engine.
- Starting MCP servers, daemons, host services, vault relays, or external agent
  runtimes.
- Changing `crates/core` dependency boundaries.

## Decisions

- The Codex harness source order becomes: user goal, `.idd/knowledge/*`,
  OpenSpec artifacts/status, ADRs, repo instructions, then AI_MERGE as evidence
  when relevant.
- The default model loop remains read-only and design-first. Implementation is
  a separate opt-in path after OpenSpec artifacts are ready.
- `rusty-idd codex env-check` should validate Rusty IDD workflow invariants
  rather than requiring stale AI_MERGE-centered phrases.
- `crates/merge-tools` owns the reusable merge phases and legacy surface
  disposition for merge goals.
- The active ADR directory is reset to one Codex harness ADR; older ADR content
  is historical input summarized in `docs/rusty-idd/merge-tools-package.md`.

## Risks / Trade-offs

- Existing AI_MERGE-heavy docs may still be useful history. Mitigation: keep
  them, but label their role as evidence/history rather than primary intent.
- The default loop becomes less aggressive about implementation. Mitigation:
  write-capable execution remains available after OpenSpec status shows the
  change is ready.
- Some older generated templates still use merge language. Mitigation: update
  harness-facing instructions first, then follow with template cleanup if the
  harness flow exposes remaining stale surfaces.

## Migration Plan

1. Replace the old active ADR set with the single Codex harness flow ADR.
2. Update `.codex` agents and loop prompts to use graph/context and OpenSpec
   status before implementation.
3. Update Codex invariant checks to reflect Rusty IDD workflow artifacts.
4. Add the Rusty IDD merge-tools package and CLI surface.
5. Update docs and skills so AI_MERGE is documented as a tool/evidence surface.
6. Validate with `rusty-idd spec status`, `rusty-idd spec validate`,
   `rusty-idd codex env-check`, `rusty-idd codex model-loop`, knowledge
   refresh, manifest refresh, and `rusty-idd validate`.
