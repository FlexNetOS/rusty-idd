# harness-control-plane

## Why

Every AI runtime re-derives "how to work here" from prose scattered across
`CLAUDE.md`, `AGENTS.md`, and the `.claude`/`.codex`/`.agents`/`.devin`
directories. That fails the same way for all models — discovery, synthesis, and
choice are lossy — and it is a token black hole (the corpus is re-injected every
session). ADR-0001, ADR-0002, and ADR-0010 already decided the cure: Rusty IDD
owns the workflow; vendor surfaces are thin adapters. The engine already has the
oracle (`spec status`/`spec next`), graph/diagram generation, and the first
stage package — but there is no single **front door** that turns repository
state into one deterministic next imperative the adapters can call.

## What Changes

- Add `rusty-idd next`: the harness control-plane front door. It resolves the
  active change (`.idd/workflow/active-change`), prints the artifact-DAG status,
  the single next ready artifact, and one scoped command to produce it —
  reusing the spec-engine oracle so there is exactly one next-step computation.
- Establish ADR-0015, unifying ADR-0001 (flow), ADR-0002 (thin front door), and
  ADR-0010 (stage packages) into one control-plane architecture, with the
  determinism front door and the (follow-up) vendor-adapter render/drift gate.
- Capture the architecture as design graphs: as-is graphs generated by the
  engine itself (dogfooded) plus authored to-be graphs.

## Capabilities

### New Capabilities
- `harness-control-plane`: the front-door imperative (`rusty-idd next`), backed
