# integrate-env-vault-relay - Design

## Context

Integration work item `work:integrate-env-vault-relay` maps capability `capability:env-vault-relay` in layer `layer:environment-security` to owner repos and validation gates generated by Rusty IDD.

## Goals / Non-Goals

**Goals:**

- Adopt the current owner/upstream surfaces before cutting local behavior.
- Keep Rusty IDD glue thin: DTO mapping, deterministic output, feature flags, validation, and CLI/API calls.
- Preserve `crates/core` as std-only.

**Non-Goals:**

- Starting host services, daemons, MCP servers, or vault relays from default Rusty IDD workflows.
- Downgrading a working upstream or owner-repo capability to simplify implementation.

## Decisions

- Implementation boundary: Feature-gate host/vault behavior; keep default Rusty IDD generation read-only.
- Add `rusty-idd knowledge integration-readiness` as the thin local boundary for this slice. It consumes generated owner surfaces and emits deterministic tool requirements, native diagnostics, feature gates, runtime assumptions, validation, and rollback without installing tools, probing Cognitum, minting credentials, mutating peer repos, or starting services.
- Treat the current `envctl` all-features test failure as upstream feature-policy evidence: `remote` and `embedded` are mutually exclusive in `crates/secrets-store-libsql`, so default Rusty IDD automation must not assume `--all-features` is valid for that owner repo.
- Treat `vault_hub/kasetto` parent-workspace capture as owner-surface evidence to route through parent `meta`/`envctl` or repo-local workspace repair, not through user-global tool installation.
- Treat Yazelix's Nix, Nushell, Lua, Ghostty, Zellij, and Beads surfaces as parent-managed toolchain/runtime requirements. They are not default Rusty IDD execution dependencies.
- Every consolidation cut must cite failing build, audit, platform, or scope evidence and include rollback.
- Adopt-first inputs:
  - `/run/media/drdave/COGNITUM`
  - `Cognitum vault on Pi Zero`

## Risks / Trade-offs

- Cross-repo ownership may require separate PRs in owner repos; this Rusty IDD change records the execution contract first.
- Native diagnostics may fail for upstream reasons; failures are evidence, not permission to pre-filter.

## Migration Plan

1. Re-read current owner repo docs, scripts, CI, and generated architecture artifacts.
2. Adopt the relevant current surfaces as-is or reference pinned upstream mirrors.
3. Run native diagnostics before cuts.
4. Apply the thinnest Rusty IDD boundary and focused tests.
5. Refresh `.idd/knowledge/*` and `.idd/MANIFEST.tsv`.
6. Run full Rusty IDD gates and owner-repo smoke tests.

## Open Questions

- A future cross-repo implementation PR should decide whether `envctl`, `vault_hub`, or `yazelix` owns each repo-local repair. This Rusty IDD slice only records readiness and keeps default generation read-only.
